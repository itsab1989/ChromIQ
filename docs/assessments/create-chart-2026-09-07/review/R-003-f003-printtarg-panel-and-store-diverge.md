Type: bug and spec conflict (per_target_settings.md §4a)
Severity: high (agree), and it is broader than printtarg: the same reload lands on every per-target row of a run created by Generate from "New run"
Steps: R2-High, run1 built with the engine. Bar: New run. Untick the engine. Set Suppress Left Clip Border off and Patch Size Scale 1.000 (traced). Preview line: `printtarg -ii1 -pA4 -t300 -m10 -M10 -c chart`. Generate.

The creator received disable_left_border=False, patch_scale=1.0 and ran `printtarg -ii1 -pA4 -t300 -m10 -M10 -c R2-High`. Sheet: clip band present, 8.0 mm patches, Left 26.0. Afterwards: panel -L ticked, -a 0,950 (shot R01/04-f003-after-generate.png); runs/run2/meta.json create_chart_settings printtarg-L True / -a 0.95; sidecar printtarg_fields -L True / -a 0.95; sidecar create_chart_settings -L False / -a 1.0.
Writer (stack): `_on_generate` 13250 -> `_align_current_run_to_target` -> `new_run()` + `_adopt_new_run_settings` (copies cache/new_run.json into run2/meta.json) -> `ctl.set_profile_run` -> main_window `_load_settings_of_visible_tab` -> `load_target_settings` -> `per_target_settings.apply` (-L True, -a 0.95, -m 10, -r False), then `_on_target_changed` 16892 loads the same again. `_collect_params` (13183) ran before, so the chart is the user's and the store is the seed block's. W1 at `_on_generate_finished` 17302 then persists the flipped widgets.
Why the seed block holds those values: it was captured on selecting "New run" while run1 (engine build) was loaded, so the hidden printtarg rows were at their defaults (-L True is the YAML default; -a 0.95 / -m 10 the i1Pro m10_a0.95 default). The block is written once (N-1) and never picks up the user's edits.
Spec: per_target_settings.md §4a quotes Knut: the block "can be modified by user to what is desired for the new run. Then when Generate Chart is pressed, all these settings are copied into the new runs parameter slot." The code copies the pre-edit block (`_adopt_new_run_settings`), then reloads it over the screen. §0 "exactly one writer" and §2.1 are also broken (the load runs while the user's edits are unsaved). The brief's known item ("the deeper ordering cause is open") is this.
Not reproduced: Agent 1's D05b claim that the executed command itself carried -L. In two Generate presses here the executed command matched the preview. Agent 1's log for that case shows a preview with `-r -c` that the executed command lacked, consistent with a reload BEFORE collect in that session (possible if the click went through a route that changes target first, e.g. the typed-name gate); I did not find such a route in `_on_generate` before line 13183. Grade for that variant: UNKNOWN.
Variant B (overwrite the same run, -L unticked again): no flip; the panel and the command agree. The fault is confined to a Generate that creates the run.
Proposed solutions, checked: Agent 1's A (seed the panel from the sidecar's create_chart_settings after the build) hides the symptom but leaves the New-run block wrong for every other row (paper, margins, patch count) and leaves W1 writing the wrong values first. B (write W1 from the params that ran) fixes printtarg rows only. The precise fix is at the cause: `_adopt_new_run_settings` should adopt the on-screen snapshot (`per_target_settings.snapshot(self)`), not the stale block, or the alignment must not trigger the visible-tab reload. Regression risk: the New-run seeding drive (scripts/drive_new_run_seeding.py, 11 checks) and scripts/drive_per_target_settings.py (74 checks) must stay green; test files: tests/test_per_target_settings*.py.
