# F-001 The "estimate" column and the "last page not full" hint disagree with the area-first chart the engine just built
Area: layout engine
Grade: OBSERVED (on screen) + INFERRED (root cause from code, reproduced offline)
Attended: unattended
Type: bug
Severity: high
Expected: Right after Generate, with nothing changed, the "Chart layout information" estimate column equals the on-screen column (same patch count, rows, strips, patch size), and the "Your patch set doesn't quite fill the last page" hint is only raised when the page really has room.
Actual: Manual, engine ON, i1Pro, A4 portrait, clip border on, default layout ("Prioritise chart area, then fit patches to it", "By patch width", instrument margins on), targen -f 400. The build produced 418 patches (22 per strip x 19 strips, 1 page, 9.23 x 9.82 mm). Immediately afterwards the estimate column read 425 total, 7 fill-up, 25 per strip, 17 strips, 1 page, 8.33 x 8.56 mm (flagged bold as differing, no explanation). During the build a hint said "there's space for about 107 more patches on it (the page holds about 525 in total)" although an area-first page is by construction full: the engine sized the patches so that the 400 fill the sheet (the layout log line says 418 (22x19), 1 page).
Further instances: D03 m12 (fixed -f 300, area-first: estimate 450 vs built 304), m14 (by-grid 12 x 18 fixed 300: 324 vs 306), m13 (patch-first fixed 300: fill-up 11 vs 15, from feeding the previous chart's total); D08b B5 (a 304-patch set loaded with the header icon, Auto count on: estimate 484 capacity fill, built 308). With Auto count on and no fixed set the estimate was exact in 55 of 55 instrument builds and 11 of 11 layout-mode builds (D02, D03).
Why it matters: The owner's priority is the layout engine, and these two panels are the engine's only feedback on capacity. Three different capacities (418 built, 425 estimated, 525 in the hint) for one unchanged layout make the numbers untrustworthy, and the hint sends the user to the patch-set editor to "fill" a page that is already full.
Steps to reproduce (click by click):
1. Open ChromIQ with no project. Create Chart, click MANUAL.
2. Type a new project name. Tick "Use the ChromIQ layout engine instead of printtarg" if it is not ticked.
3. ChromIQ layout: Instrument i1Pro, Paper A4 Portrait, Clip border On; leave Create layout at "Prioritise chart area, then fit patches to it".
4. Open "targen parameters", untick Auto next to -f and set 400.
5. Click Generate Chart. Click OK on the "doesn't quite fill the last page" window.
6. Read the two columns of "Chart layout information".
Evidence: Screenshots/A1-engine-vs-printtarg/02-engine-built-window.png (both columns visible), Test Runs/logs/d01_02-engine-built.json (actual/estimate dicts, log tail with "418 patches (22x19), 1 page"), Test Runs/logs/d01_engine_vs_printtarg.log (hint text with 107 / 525), offline reproduction in the checkpoint-01 notes.
Root cause (INFERRED, reproduced offline): `workflow/layout_engine/chart.py:build_chart` passes `area_target_count=len(target.patches)` into `instruments.geom_from_build_kwargs`, so area-first sizes the patch from the real count (offline: 22 x 19 = 418 at 9.21 x 9.86 mm). The estimate (`ui/tabs/tab_chart.py` around line 5578, `geom_from_build_kwargs(r.build_kwargs())`) and the hint (`_partial_last_page_blank`, around line 18436) call the same function WITHOUT `area_target_count`, so they size the patch for a capacity fill (25 x 21 = 525 per sheet at 8.33 x 8.56). The estimate also feeds `_onscreen_patch_total()` = the .ti2 NUMBER_OF_SETS (418, already padded) instead of the designed 400 (.ti1), and pads it again to 425; `_estimate_patch_total`'s own docstring names this trap for presets but the on-screen fallback still has it.
Spec or source cited: none covers this directly; `docs/design/per_target_settings.md` is not involved. The panel's own tolerance note (`ui/chart_layout_info_panel.py` _PATCH_TOL_MM) shows the two columns are meant to agree to a pixel.
Possible solutions (no code): A. Feed the same `area_target_count` (designed patch count from the .ti1, or the -f value / attached set) into the estimate and hint geometry so they use the sizing the build uses. B. Make the estimate lay out the designed count (.ti1 NUMBER_OF_SETS) rather than the padded .ti2 total. C. Suppress the "last page not full" hint for area-first recipes, where the page is full by definition. D. When the two columns differ, print one line saying why (for example "estimate assumes a full page of default-size patches").
Regression risk if changed: Medium. The estimate feeds the Guided patch-count headline and the Manual command preview; changing the geometry inputs will move numbers users have seen for months. Patch-first charts are unaffected by A (no area_target_count use) but affected by B.
Needs owner decision: no (it is a correctness fix), but he should say whether the hint should stay for area-first charts at all.
