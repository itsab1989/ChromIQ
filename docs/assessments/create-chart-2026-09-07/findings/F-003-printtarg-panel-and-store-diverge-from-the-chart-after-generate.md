# F-003 After a printtarg Generate, the printtarg panel and the per-target store carry -a0.95 and "Suppress Left Clip Border" on, while the chart was built with -a1.0 and the clip border present
Area: manual (printtarg path) / run bar (per-target store)
Grade: OBSERVED (panel and files); the exact writer is INFERRED
Attended: unattended
Type: bug (known family: build-in-flight clobber, listed as open in the brief)
Severity: high
Expected: After Generate, the panel shows the values the chart was built with, and W1 (per_target_settings.md section 3, "Generate Chart writes Create Chart's settings for that target") stores those same values.
Actual: Manual, engine OFF, fresh run (run2). Before Generate the driver read the widgets: -L raw=False (clip border kept), -a raw=1.0; the command preview read `printtarg -ii1 -pA4 -t300 -m10 -M10 -c chart`. The chart came out with the 26 mm clip border (Measured from Preview: Left 26.0) and the sheet's own stamp shows the same command with no -L and no -a. After the build the panel shows Patch Size Scale 0,950 and "Suppress Left Clip Border" ticked. On disk, run2's own sidecar contradicts itself: `create_chart_settings` says printtarg-L False, printtarg-a 1.0 (what ran), `printtarg_fields` says -L True, -a 0.95; and runs/run2/meta.json `create_chart_settings` stored -L True, -a 0.95. The same wrong pair is also stored in run1 (the engine build), where the printtarg widgets were hidden.
Why it matters: The store now says the run was made with a chart it was not made with. Pressing Generate again ("Run 2 (overwrite)") would build a smaller-patch chart without the clip border, unlike the one on screen; switching runs and back restores the wrong values; and the engine OFF-to-ON conversion (Knut #3) faithfully carried the wrong values into the engine recipe (recipe after the round trip: clip_border False, pscale 0.95). The value 0.95 with -L on is the i1Pro shipping printtarg default (m10_a0.95), which points at an instrument-default seeding running after the build.
Second reproduction (D05b, 08:52, project A5-Furniture run2, unattended): engine toggled OFF in a fresh run; raw widget values read by the driver before the click: -L False, -a 1.0, -m 6; command preview: `printtarg -ii1 -pA4 -t300 -M6 -r -c chart`. Immediately after the Generate click the -L widget read True; the runner log shows the command actually executed: `printtarg -ii1 -pA4 -t300 -L -M6 A5-Furniture` (with -L, without -r -c). So the preview and the executed command differ, and the widget is flipped at Generate time (not only after the build). The setting `i1pro_chromiq_clip_style` was false in the sandbox, so the ChromIQ clip style is not the cause; the two triple-density paths that call `_manual_lb_pw.set_value(True)` (tab_chart.py:7477, 19458) were not in play (CM only). The writer that flips -L at Generate was not identified in the time available (INFERRED unknown).
Steps to reproduce (click by click):
1. New project name in MANUAL, untick "Use the ChromIQ layout engine".
2. printtarg parameters: Instrument i1Pro, A4, leave Suppress Left Clip Border unticked and Patch Size Scale 1.000. targen -f 400.
3. Generate Chart. Watch the two controls after the preview appears.
Evidence: Screenshots/A1-engine-vs-printtarg/03-engine-off-before-generate.png and 04-printtarg-built-window.png (0,950 and ticked box after; the stamp on the sheet shows the command), Test Runs/logs/d01_engine_vs_printtarg.log (raw widget values at 07:50:35, command preview at 07:50:36), Test Runs/logs/d01_04-printtarg-built.json, files /Users/Basti/ChromIQ-assessment/A1-EngineVsPrinttarg/runs/run2/A1-EngineVsPrinttarg.channels.json and meta.json (both records quoted in Reports/checkpoint-01-launch-and-a1.md).
Spec or source cited: docs/design/per_target_settings.md section 3 (W1) and section 4c "An instrument default is not an override" (confirmed behaviour), which this contradicts: an instrument default overwrote a person's answer after the build. The brief's known-item note: `_apply_ui_state` guards via `_layout_owned_by_build`, "the deeper ordering cause is open and awaiting the owner".
Possible solutions (no code): A. Make the post-build restore (`_restore_chart_settings` / `_apply_ui_state`) seed the printtarg widgets from the sidecar's `create_chart_settings` (the record that is right) rather than from the instrument default. B. Write W1 from the ChartParams that were actually sent to the tool, at Generate time, and forbid any later writer for that build. C. At least make `printtarg_fields` and `create_chart_settings` come from one snapshot so the sidecar cannot disagree with itself.
Regression risk if changed: Medium-high. This is the seeding order the brief calls open; the clobber guard already exists for the engine panel and a second guard for printtarg widgets must not re-break presets that legitimately set -L/-a after loading.
Needs owner decision: yes. Which record is the truth for a run: what Generate ran with, or what the panel showed a second later?
