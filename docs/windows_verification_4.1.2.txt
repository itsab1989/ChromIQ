ChromIQ 4.1.2 — Windows verification (kick-off prompt)


WHY YOU ARE DOING THIS
======================
ChromIQ 4.1.2 has been through ten betas. Every line of it was written, measured
and reviewed on macOS. Not one line has ever run on Windows. Sebastian wants to
take 4.1.2 out of beta and ship it stable, and he will not do that on a platform
nobody has looked at.

FINDING A REAL WINDOWS PROBLEM IS THE SUCCESS CASE. This is not a formality to
be signed off. A clean run means "ship it"; a problem found means "we did not
ship a broken build to every Windows user" — both are wins, and only one of them
is available by hurrying. Report what you actually saw, including the things you
could not settle.

You will be told, below, exactly which failures and skips are EXPECTED on
Windows for reasons that are not bugs. Read that section before you run anything.
The point of it is that when something outside that list goes wrong, it stands
out instead of drowning.


WHAT "4.1.2" MEANS HERE
=======================
  * master is v4.1.2-beta.7 (commit 95f3a2ac) and holds betas 1-7.
  * Branch perf/startup-snappiness adds betas 8, 9, 10 on top (tag
    v4.1.2-beta.10, commit 75764688).
  * The branch contains master, so checking out the branch gives you all ten.

The startup/appearance work in betas 8-10 is where nearly all the Windows risk
is, and most of this prompt is about it. Betas 1-7 get three short checks at the
end (step 9) — they are unverified on Windows too, just less dangerous.

================================================================================
Report, as a short block at the top of your final report:

  * Which shell your Bash tool is really running. Run these; one will work:
        uname -s                  -> "MINGW64_NT-..." = Git Bash, "Linux" = WSL
        $PSVersionTable.PSVersion -> PowerShell

    (Claude Code on native Windows normally uses Git Bash. Confirm rather than

  * Processor architecture: x64 or ARM64.  echo %PROCESSOR_ARCHITECTURE%  /
    $env:PROCESSOR_ARCHITECTURE  /  uname -m
  * Display resolution and the Windows display scale (100% / 125% / 150% / …).
  * Number of CPU cores, and RAM.
  * Python version available (aim for 3.13 — that is what the Windows release is
    built with; the macOS baseline below was taken on 3.14, so a small test-count

SHELL SYNTAX — the only table you need. Pick your column once and stick to it.

  purpose                | Git Bash                  | PowerShell            | cmd
  -----------------------|---------------------------|-----------------------|---------------------
  set a variable         | export X=y                | $env:X="y"            | set X=y
  set it for one command | X=y cmd...                | $env:X="y"; cmd...    | set X=y && cmd...
  path separator         | / ; "C:\like\this" quoted | \                     | \
  run the venv's python  | .venv/Scripts/python.exe  | .venv\Scripts\python.exe | .venv\Scripts\python.exe

DO NOT ACTIVATE THE VENV. "activate", "Activate.ps1" and "source .../activate"
are three different commands with three different failure modes, and
PowerShell's ExecutionPolicy blocks one of them out of the box. Call
.venv\Scripts\python.exe directly, every time. It works in all three shells and
cannot half-succeed.

Git Bash note: it rewrites arguments that look like Unix paths. When you pass a
Windows path to a program, write it Windows-style ("C:\Program Files\...") and
quote it.

STEP 2 — PYTHON ENVIRONMENT  (there is one Windows trap here)
================================================================================
    py -3.13 -m venv .venv          (or python -m venv .venv)
    .venv\Scripts\python.exe -m pip install --upgrade pip

THE TRAP: requirements.txt pins pycups, which only builds on macOS and Linux.
`pip install -r requirements.txt` WILL FAIL ON WINDOWS AND THAT IS NOT A BUG.

    PowerShell: Select-String -NotMatch 'pycups' requirements.txt | %{$_.Line} | Set-Content requirements-win.txt

    .venv\Scripts\python.exe -m pip install -r requirements-win.txt
    .venv\Scripts\python.exe -m pip install -r requirements-dev.txt

(pyobjc is already correctly marked macOS-only and will skip itself. Do not
delete requirements-win.txt afterwards, and do not commit it.)

Sanity check before going further:

    .venv\Scripts\python.exe -c "import PyQt6, PyQt6.QtWebEngineWidgets, PIL, numpy, tifffile, freetype; print('imports ok')"

On ARM64 specifically, note whether every wheel installed or anything was built
from source — core/freetype_bootstrap.py exists solely because Windows/ARM64
needs a vendored FreeType, so ARM64 is the arch where this step can bite.

BACK UP THE SETTINGS STORE NOW, BEFORE ANYTHING WRITES TO IT:

    reg export HKCU\Software\ChromIQ %USERPROFILE%\chromiq-settings-backup.reg

HKCU\Software\ChromIQ\ChromIQ. It may not exist yet — that is fine and means you

That is why step 4 comes before step 6. To get back to a clean profile later:

    reg delete HKCU\Software\ChromIQ /f

STEP 4 — FIRST LAUNCH: no ArgyllCMS, clean profile  (highest-value single test)
================================================================================
    .venv\Scripts\python.exe main.py

Watch the screen from the moment you press enter, and screenshot it. LOOK at the
screenshots — you can read PNGs, so most of the visual judgement here is yours,
not Sebastian's.

HOW TO SCREENSHOT (Pillow is already installed, and ImageGrab works on Windows):

    .venv\Scripts\python.exe -c "from PIL import ImageGrab; ImageGrab.grab().save(r'C:\Users\<you>\shot.png')"

To catch the splash you must shoot WHILE it is up, so start the app in the
background and shoot on a short delay — e.g. a tiny script that launches
main.py with subprocess.Popen, then grabs at 0.2 s, 0.5 s, 1 s, 2 s and 4 s.
Five shots of one launch tell you far more than five launches watched by eye,
and they timestamp themselves.

What is supposed to happen: a small ChromIQ splash picture appears almost
immediately (fractions of a second, not seconds), stays while the app builds,
and disappears when the main window opens.

Three specific things to answer:

 4a. DID THE SPLASH APPEAR AT ALL, AND WHEN?
     Wrong: nothing on screen for two or three seconds and then a brief flash
     just before the main window. That is the exact fault this branch was written
     to fix, coming back.
     The splash waits up to 0.3 s for Windows to confirm it is on screen and then
     gives up and carries on. On a virtual machine with software rendering, or
     over Remote Desktop, that confirmation can be slow. So if it does not
     appear: say whether you are on a local console or a remote session, and
     re-test after switching "Classic splash screen" on (step 8b). "Windows is
     broken" and "this VM is slow to composite" are different findings and the
     difference matters.

 4b. IS THE SPLASH THE RIGHT SIZE AND IN THE RIGHT PLACE?
     Right: about 640 x 400 logical pixels, centred on the screen, the artwork
     filling it edge to edge.
     Wrong: twice as large with the picture crammed into the top-left quarter.
     That happened once already on macOS (it was sized in device pixels instead
     of logical ones) and Windows display scaling is exactly where it would come
     back. Record the pixel size you measure and the display scale you are at.

 4c. THE "ARGYLLCMS NOT FOUND" DIALOG.
     With no Argyll installed, the app opens this dialog DURING startup, while
     the splash is still up — and the splash is set to stay on top of other
     windows. On macOS you can click the splash away to reach the dialog. On
     Windows, a modal dialog normally blocks clicks to the app's other windows,
     so that escape may not work.
     Wrong: a dialog you cannot see or cannot reach, or an app that looks frozen.
     This is the first thing every Windows user with a fresh machine will meet,
     so spend time here. Report exactly what you saw: was the dialog on top, or
     behind the splash? Did clicking the splash dismiss it? Did Alt+Tab help?
     Could you dismiss the dialog and reach the main window?

Then let the app finish opening and note whether the Welcome dialog appears
(expected on a fresh profile, about a tenth of a second after the window) and
whether anything is visibly wrong with the main window. Screenshot it. Quit.

--- EXPECTED ON WINDOWS, NOT BUGS -----------------------------------------------

E1. MANY MORE SKIPS THAN 101. Under QT_QPA_PLATFORM=offscreen, Windows exposes an
    EMPTY font database — every font family resolves to a null font. The suite
    knows this (tests/_fontcheck.py) and skips anything measuring text widths.
    Eleven files, 179 tests between them, hold those guards:
      test_button_text_fits, test_choice_dialog_button_width,
      test_disabled_controls_look_disabled, test_file_guide_structure,
      test_help_card_width, test_knut_beta77_batch, test_masthead_center_fits,
      test_report_pdf_layout, test_target_bar_stability,
      test_target_bar_alignment, test_translation_integrity
    Expect tens of extra skips here. IMPORTANT CONSEQUENCE: the offscreen gate on
    Windows is structurally blind to button-label fitting — which is one of the
    four filters this branch merged together. That is why step 7 exists. Do not
    treat a green gate as covering it.

E2. "chromiq-chartread helper not built" (six files) and the gamut helper: those
    .exe files are produced by the CI build, not by a source checkout. Expected.

E3. macOS-only tests skip: /dev/cu.* serial exclusion, the Homebrew symlink farm,
    "needs macOS sips to rasterise", "Generic CMYK profile not installed",
    "probe result TIFFs not present".

E4. test_target_instrument_gate has one test hard-wired to
    /Applications/Argyll/bin/chartread with no fallback — it skips on Windows
    however Argyll is installed. A test limitation, not a bug.
    (Five other files hard-code that path but fall back to a PATH lookup first,
    which is why step 5 put Argyll on PATH — with PATH set they RUN.)

E5. faulthandler_timeout is 90 s. On a slow VM a heavy test can pass that and dump
    every thread's stack to stderr. Alarming; not a failure. Judge by the final
    pass/fail line.

E6. tests/test_settings_dialog_opens_full_size.py is NEW on this branch and asserts
    absolute pixel sizes (height >= 700, width >= 1040) with NO font guard. With
    the empty offscreen font DB it may well fail. DO NOT report that as a
    regression from the offscreen run — re-run it in step 7 with real fonts and
    judge it there.

E7. Printing: pycups and the CUPS path are macOS/Linux only. test_cups_printer only
    builds command strings, so it still passes.

WHAT IS NOT EXPECTED, i.e. report it loudly: any failure in a file not listed
above; any ERROR (as opposed to failure) — errors usually mean a fixture blew up,
often Argyll or a path; any test that HANGS (if the run appears stuck, rerun with
--timeout=300 --timeout-method=thread if pytest-timeout is available, so the stack
names the test).

Give me: the final counts, the full list of failures/errors with their assertion
text, and the skip list from -rs grouped by reason, compared against the macOS
skip catalogue in the appendix.

STEP 8 — TARGETED CHECKS ON THE FOUR THINGS THAT CHANGED
================================================================================
Do these with the app running for real. Screenshot each and look at the
screenshots yourself.

 8a. LIGHT AND DARK — and please read this before you start.
     Windows almost certainly starts this app in LIGHT mode (the app follows the
     system colour scheme, and Windows 11's default app mode is light). Nearly
     all the macOS work was done in dark. Light is also where this branch put its
     newest code. So light is not the afterthought here, it is the main event.
     First confirm which mode you are actually in:
        .venv\Scripts\python.exe -c "from PyQt6.QtWidgets import QApplication; a=QApplication([]); print(a.styleHints().colorScheme())"
     Then, in the app, do everything below in BOTH modes (Preferences → Appearance).

 8b. THE SPLASH, THREE WAYS.
     - normal (already done in step 4)
     - Preferences → Beta → "Classic splash screen" ON, restart. The old Qt splash
       comes back. It should look the same and take about a second longer. Confirm
       the switch is visible in the dialog, is worded sensibly, and survives a
       restart.
     - display scaling: relaunch with QT_SCALE_FACTOR=1.5, then 2. The splash must
       stay proportionate and centred, not double-size with the art in a corner.
       (This is a proxy for Windows display scaling that costs no sign-out. If you
       can also set the real Windows scale to 150% once and relaunch, do — but
       report which method produced which result.)

 8c. THE COMPOSITE EVENT FILTER — the highest Windows risk on the branch.
     Four app-wide filters became one object. One of them (tooltip word-wrapping)
     exists BECAUSE of Windows, issue #70. Compare the app with and without the
     change, in the same session, on the same screens:
        normal:            (nothing to set)
        old behaviour:     CHROMIQ_SEPARATE_FILTERS=1
     Check in both: hover several long tooltips, including one near the right edge
     and one near the bottom edge of the screen (wrong = runs off the screen, or
     one long unwrapped line); open Preferences and a couple of dialogs and look
     for clipped or overlapping button labels; check group-box panels have their
     usual background; press the space bar right after a dialog opens (wrong = it
     activates whatever button had focus).
     If anything differs between the two, that is the finding of the whole
     exercise — say so clearly and screenshot both.

 8d. THE TAB PANE RULE.
     Click through all five tabs a few times, both themes.
     - Watch the thin line directly under the tab strip. It is now one fixed
       colour for every tab. On macOS it is completely hidden behind the tab bar.
       ON WINDOWS IT MAY NOT BE. If you can see a line there that used to take the
       tab's colour, that is a visible change on Windows and a genuine finding.
       Screenshot each tab and compare the strip area.
     - Open the SAME dialog from two places and check they look identical:
       the measurement report from the Measure tab vs from the Tools menu; and
       Preferences from Create Chart's "Edit layout defaults" vs from the gear.
       Wrong = a coloured hairline inside the dialog, or a missing frame in light
       mode, depending on where you opened it from.
     - Launch the app and go straight to Create Chart WITHOUT visiting other tabs.
       It must already look like the rest of the app. Wrong = panels a different
       shade that only come right after you switch away and back.

 8e. THE LOG FONT.
     Switch light → dark → light in Preferences and watch the log panel at the
     bottom of a tab, especially its greyed-out placeholder text when empty.
     Wrong = the text stays noticeably bold after switching to dark.
     This one needs a FRESH profile to reproduce reliably (reg delete
     HKCU\Software\ChromIQ /f first), because hiding the log panes hides it.

 8f. TIMINGS. The app logs to %LOCALAPPDATA%\ChromIQ\Logs\chromiq.log. Each launch
     writes a "=== ChromIQ session started" banner, then a "ChromIQ <version>
     starting; python=..." line, then "MainWindow initialised", then "Event loop
     starting". Take the gap between the "ChromIQ ... starting" line and "Event
     loop starting" — that is a like-for-like number. Do 3 launches and give the
     range, in both themes, and note that timings on a VM are indicative only.
     macOS reference on the same commit: about 3.0 s from click to painted window,
     tab switch about 9 ms. If Windows is dramatically worse (say 8 s+), that is
     worth reporting even though it is not a correctness bug.

A SUBAGENT — ONE, READ-ONLY, WHILE THE GATE IS RUNNING
================================================================================
Start it when you start step 6 and not before; it costs no wall time then. It
MUST NOT launch the app, take over the desktop, change display settings, or
touch the registry — you and it share one desktop, one settings store and one
Argyll process guard, and two agents driving Qt at once manufactures failures
that nobody can reproduce. Everything requiring the running app stays with you,
in order.

Its brief: a paper audit of the branch for Windows assumptions.
    git diff 95f3a2ac 75764688
  - Every sys.platform / os.name branch the changed code can reach, and what the
    Windows arm does.
  - CompositeAppFilter in ui/widgets.py: its _INTERESTING set is {Polish, Show,
    StyleChange}. Confirm from the source that all four sub-filters really act on
    no other event type, and that none of them consumes an event by returning
    True. (I believe this holds; get it confirmed independently.)
  - ui/splash.py PlainSplash: device-pixel-ratio arithmetic, window flags, and
    what happens on a fractional Windows scale factor.
  - resolve_mode() in ui/theme.py: what QStyleHints.colorScheme() reports on
    Windows and whether the seeded _title_bar_mode can ever disagree with the
    stylesheet actually applied.
  - A list of what the offscreen gate on Windows structurally cannot see.
It reports findings with file and line, and marks each as "certain from the
source" or "needs checking on the machine". It does not change any file.


================================================================================
APPENDIX A — WHAT BETAS 8-10 ACTUALLY CHANGED
================================================================================
Only these files changed: main.py, ui/splash.py, ui/main_window.py,
ui/widgets.py, ui/dialogs/settings_dialog.py, core/settings.py, the i18n JSONs,
CHANGELOG, version, and six test files. 798 lines added, 50 removed. Nothing in
the printing, measuring or profiling paths was touched.

 1. THE SPLASH. Qt's own QSplashScreen spends about a second inside show()
    waiting for something that never becomes true. It is now a plain frameless
    always-on-top window painting the same picture, which waits (up to 0.3 s) for
    the window to actually be exposed and then carries on. It was sized from the
    wrong pixel units once already and came up double-size with the artwork in a
    quarter. "Classic splash screen" in Preferences → Beta restores the old one.
 2. THE EVENT FILTERS. Four application-wide filters became one CompositeAppFilter
    that calls the same four in the same order Qt would have (reverse install
    order) and returns immediately for event types none of them care about. About
    a second of a five-second launch. CHROMIQ_SEPARATE_FILTERS=1 restores the four
    separate installs. One of the four, the tooltip word-wrapper, exists because
    of Windows (issue #70) — THIS IS THE HIGHEST WINDOWS RISK ON THE BRANCH.
 3. THE TAB PANE STYLESHEET. It used to carry the current tab's accent colour, so
    every tab switch re-applied a stylesheet and re-drew all five tab trees — a
    quarter of a second per switch, now under a hundredth. It is now one string
    for every tab, scoped to this one tab widget (unscoped, it leaked into dialogs

    hidden behind the tab bar; ON WINDOWS IT MAY NOT BE, and if it is visible this
    became a visible change. That is the single most likely Windows-only
    regression on the branch.
 4. THE THEME SEED AND THE LOG FONT. The window used to assume dark before the
    real theme was known, which cached every tab's styling under the wrong theme
    and left Create Chart wrongly styled on launch until you switched tabs. It now
    seeds from the resolved appearance, and clears the per-tab style cache when a
    LIGHT theme is applied. Separately, apply_theme now sets the log's viewport
    font as well as the widget's, which was leaving the log bold after a switch to
    dark.

Note what item 4 means for you: WINDOWS WILL PROBABLY RUN THE LIGHT BRANCH BY
DEFAULT, and the light branch is the newest code here.
