--------------------------------------------------------------------------------
  A7.  The CMYK -> RGB conversion, and the 10^-6 step - accept or push back
       OWNER: KNUT               Cheap
--------------------------------------------------------------------------------

  Measured on your own FOGRA51 file, 1 617 patches, through ChromIQ's own colour
  code: the textbook subtractive->additive conversion is out by 12,10 dE00 on
  average, with 7 patches of 1 617 (0,4 %) landing within 2,5. The paper patch
  alone misses by more than twice the tolerance the standards allow for paper.
  It cannot be repaired with a better formula, because CMYK in a
  characterization file is a control signal for one specific press, not a
  colour.

  The 10^-6 perturbation does not change the file: FOGRA51 carries Lab to two
  decimals, so adding a millionth and writing back at the file's own precision
  produces a byte-identical file - and the protection on a measured dataset does
  not turn on byte comparison.

  The route that does work: use the dataset's own Lab column as the aim, discard
  its device column, and get the RGB from the user's own printer profile.

  (Accept the finding, or push back.)

--------------------------------------------------------------------------------
  B6.  Is this the settings model? Preferences is a stencil, not a control.
       OWNER: KNUT (it extends a ruling you have already given)
       NOT cheap to reverse
--------------------------------------------------------------------------------

  Three tiers: FACTORY (shipped constants, immutable) -> MY DEFAULT
  (Preferences) -> THIS RUN'S VALUES (copied from Preferences once, the first
  time a set is chosen for that run). From that moment the run owns its numbers
  and nothing in Preferences can reach them - not editing, not Restore Factory
  Defaults, not an upgrade.

  Two consequences worth stating out loud: two runs in one project can
  legitimately hold different values for the same metric because they were
  started on different days, so the report must print the set and the values it
  used, per run; and an upgrade that changes a factory value must keep the
  user's value and say "factory value changed from X to Y in this release" with
  a one-click restore, rather than silently adopting the new number.

  (Confirm the three tiers, or change them.)

  B8.  Do we bundle the Idealliance reference ICC profiles, and compute aims
       through them?
       OWNER: SEBASTIAN          Adding is cheap; users then depend on it
--------------------------------------------------------------------------------

  Two related things. First, may ChromIQ include the Idealliance / X-Rite
  reference ICC profiles? Their licence is the one explicit grant in this whole
  family: "may be used, embedded, exchanged, and shared without restriction. It
  may not be altered, or sold without written permission." Second, ChromIQ could
  CALCULATE the aim colours for GRACoL2013, SWOP2013 and CRPC 1-7 through one of
  those bundled profiles - putting those reference conditions in the app without
  redistributing anybody's dataset. The machinery already exists in ChromIQ.

  The catch, and it is permanent: an ICC profile is a fitted, smoothed MODEL of
  the characterization data, not the data. Its own fitting error sits on top of
  a tolerance whose practical floor ISO itself calls impractical to go below. So
  aims computed this way are close, not equal.

    (a) Bundle the profiles and offer computed aims, clearly named - "aims
        computed through the GRACoL2013 reference profile" - never as the silent
        default.
    (b) Bundle the profiles for colour conversion only, and do not compute aims
        from them.
    (c) Bundle nothing.

  We recommend: (a), on those exact terms. The label must say the aims were
  computed through a profile, so that a user who needs the real dataset knows to
  go and get it.

--------------------------------------------------------------------------------
  C2.  The 95th-percentile estimator - round or ceil?
       OWNER: SEBASTIAN (it changes a shipped number), with KNUT on which
       belongs on an ISO row          NOT cheap to reverse
--------------------------------------------------------------------------------

  "The 95th percentile" means "ignore the worst 5 % of patches and report the
  worst of what's left". There are two standard ways to pick where the cut
  falls, and they differ by one patch. ChromIQ rounds; the textbook nearest-rank
  method rounds up. On a 918-patch chart that is patch 872 versus 873; on a
  72-patch wedge, one rank can be the difference between a pass and a fail. Both
  ISO tables specify a 95th percentile and NEITHER names an estimator, so there
  is no right answer to look up. Whichever is chosen becomes a published
  property of every report ChromIQ produces.

    (a) Keep ChromIQ's current method everywhere.
    (b) Change to nearest-rank everywhere.
    (c) Keep ChromIQ's for ChromIQ's own sets; use nearest-rank for any row
        labelled with a standard's name.

  We recommend: (c), and the report must print which was used. It changes no
  existing ChromIQ number, so nobody's saved report shifts.
